# Week 3: Evaluator Development, Docker Sandboxing and Testing

## Work Completed

During Week 3, I continued developing the coding benchmark evaluator from Week 2. The main focus was completing the evaluation pipeline, introducing Docker-based sandboxing, and testing the evaluator on a small benchmark subset.

### Evaluator Development

Extended the evaluator to handle the complete model evaluation workflow.

The evaluator was improved to:

* Extract Python code from model responses.
* Execute generated solutions against benchmark test cases.
* Support both function-based and stdin/stdout-based problems.
* Capture program output and execution errors.
* Classify solutions as pass or fail.
* Track token usage and generation time.
* Save results incrementally.
* Resume evaluations after interruption.

This made the evaluator suitable for running larger benchmark evaluations without losing previously completed results.

### Docker Sandbox Implementation

Since the evaluator executes code generated by an LLM, running the code directly on the host system could introduce security risks. To address this, Docker was integrated as an isolated execution environment.

A Python-based Docker image was created for executing generated benchmark solutions:

```bash
docker build -t benchmark-python .
```

The Docker environment was configured with several restrictions:

* Network access disabled
* Read-only filesystem
* Limited memory
* Limited CPU usage
* Process limits
* Non-root execution
* Temporary filesystem for runtime operations
* Restricted privilege escalation

This provided a controlled and isolated environment for executing untrusted model-generated code.

### Evaluator and Docker Integration

The evaluator was modified so that generated solutions were executed inside the Docker sandbox rather than directly on the host machine.

The resulting evaluation pipeline was:

```text
Benchmark Problem
       ↓
Ollama / Qwen2.5-Coder
       ↓
Generated Python Code
       ↓
Code Extraction
       ↓
Docker Sandbox
       ↓
Benchmark Tests
       ↓
Evaluation Result
```

### Initial Testing

Before running the evaluator on the complete benchmark, I tested the pipeline on a small subset of problems:

```bash
python evaluate_ollama_docker.py --dataset "coding_benchmark.jsonl" --model "qwen2.5-coder:1.5b" --output "test_results.jsonl" --limit 10
```

This test verified the interaction between the benchmark dataset, Ollama, the evaluator, and the Docker execution environment.

### Debugging and Failure Classification

Testing revealed several different failure scenarios. The evaluator was improved to distinguish between:

* Correct solutions
* Wrong answers
* Syntax errors
* Runtime errors
* Timeouts
* Incorrect output

Some function-based solutions generated by the model also included additional `print()` or `assert()` statements. These could interfere with benchmark execution, so the evaluator was adjusted to handle such generated code appropriately.

## Key Observation

Running a small-scale evaluation before the full benchmark helped identify issues in code extraction, execution, Docker isolation, and failure classification.

This testing phase was important for ensuring that the evaluator was reliable before scaling it to a larger number of benchmark problems.

## Outcome

By the end of Week 3:

* The evaluator supported the complete model-generation-to-evaluation workflow.
* Docker sandboxing was integrated for safer code execution.
* Function-based and stdin/stdout problems were supported.
* Execution failures were classified into different categories.
* Incremental result saving and evaluation resumption were implemented.
* The complete pipeline was successfully tested on a sample of benchmark problems.

The evaluator was now ready for further refinement and larger-scale model evaluation.
